# 音频管线

从麦克风到扬声器的完整链路，以及每个环节的参数与取舍。

## 参数总表

| 参数 | 值 | 定义位置 |
| --- | --- | --- |
| 采样率 | 16 000 Hz | `AudioConfig.SAMPLE_RATE` |
| 帧长 | 20 ms | `AudioConfig.FRAME_MILLIS` |
| 帧采样数 | 320（16 位单声道 PCM） | `AudioConfig.FRAME_SAMPLES` |
| 编解码 | Opus，`OPUS_APPLICATION_VOIP`，单声道 | `OpusCodec.kt` |
| Opus 实现 | Concentus 1.0.2（纯 JVM） | `app/build.gradle.kts` |
| 码率（WiFi / Nearby / 回环） | 24 000 bps | `OpusCodec` 默认值 |
| 码率（蓝牙） | 16 000 bps | `BluetoothRoomSession.BLUETOOTH_BITRATE` |
| 编码暂存缓冲 | 512 B | `OpusCodec.encBuf` |
| 采集源 | `VOICE_COMMUNICATION` | `AudioEngine` |
| 回声消除 | `AcousticEchoCanceler`，可用时启用 | `AudioEngine` |
| 播放属性 | `USAGE_VOICE_COMMUNICATION` + `CONTENT_TYPE_SPEECH`，`CHANNEL_OUT_MONO`，`MODE_STREAM` | `AudioEngine` |
| 缓冲区大小 | `max(minBufferSize, FRAME_SAMPLES * 4)`，录制与播放同规则 | `AudioEngine` |
| 音频模式 | 入房 `MODE_IN_COMMUNICATION`，离房 `MODE_NORMAL` | `MainActivity.setCommunicationMode` |
| 音频焦点 | `AUDIOFOCUS_GAIN_TRANSIENT_EXCLUSIVE`，接受延迟授予，被压低时暂停 | `AudioFocusChange` |
| 抖动缓冲预缓存 | 3 帧 | `JitterBuffer` |
| 抖动缓冲上限 | 10 帧 | `JitterBuffer` |
| VAD 阈值 | RMS 500.0 | `SpeakingDetector` |
| VAD 挂起 | 15 帧（约 300 ms） | `SpeakingDetector` |
| 蓝牙发送队列音频容量 | 3 帧 | `BluetoothSendQueue` |

选 16 kHz 宽带单声道是语音场景的常规折中：比 8 kHz 窄带清晰得多，又远比 48 kHz 省带宽与 CPU。20 ms 帧长是 Opus 的默认甜点，兼顾编码效率与延迟。

## 链路

```mermaid
flowchart LR
    MIC["麦克风<br/>VOICE_COMMUNICATION"] --> AEC["AEC 回声消除"]
    AEC --> GATE["MicGate<br/>静音门控"]
    GATE --> ENC["OpusCodec<br/>编码"]
    ENC --> TX["传输层"]
    TX -.->|"网络"| RX["传输层"]
    RX --> JB["JitterBuffer<br/>每个远端一个"]
    JB --> DEC["OpusCodec<br/>解码 / PLC"]
    DEC --> MIX["Mixer<br/>饱和相加"]
    MIX --> SPK["扬声器<br/>AudioTrack"]
```

节拍由**阻塞式 `AudioTrack.write` 提供**——写满即阻塞，天然形成 20 ms 的时钟，不需要额外的定时器。

## 采集侧

`AudioEngine` 是唯一接触 `AudioRecord` / `AudioTrack` 的类，内部通过 `AudioIo` 接口隔离，因此会话层的测试可以注入 fake。

`MicGate` 决定是否真的发送：

```kotlin
effectiveMuted = userMuted || focusInterrupted
```

两个条件独立。这意味着**音频焦点恢复不会清除用户手动设置的静音**——这是被单元测试明确锁定的行为。

## 音频焦点

请求类型是 `AUDIOFOCUS_GAIN_TRANSIENT_EXCLUSIVE`，并且 `acceptsDelayedFocusGain = true`、`willPauseWhenDucked = true`。

| 焦点变化 | 行为 |
| --- | --- |
| `LOSS` 系列 | 切换为只听模式（不发送，仍接收播放） |
| `GAIN` | 恢复发送（除非用户手动静音） |
| 未知变化码 | 保持原状态不变 |

请求结果映射为 `GRANTED` / `DELAYED` / `DENIED` 三态。被其他应用（来电、导航播报）抢占时**不会掉线**，只是降级为只听。

## 抖动缓冲

每个远端流一个 `JitterBuffer`。内部是一个以 16 位序号**解回绕成单调 `Long`** 为键的有序映射。

行为规则：

- **预缓存**——必须先攒够 3 帧才开始输出，用于吸收网络抖动。
- **乱序重排**——序号靠后的包先到会被暂存，按序输出。
- **丢包**——该位置 `poll()` 返回 `null`，调用方把 `null` 喂给 `OpusCodec.decode` 触发 **Opus PLC**（丢包补偿），生成一个听感平滑的插值帧，而不是留一段静音。
- **迟到丢弃**——起播后序号小于当前位置的帧直接丢掉。
- **溢出**——超过 10 帧时丢最旧的。
- **欠载**——不推进位置指针；若空洞大于缓冲上限，则重新对齐到当前最小序号。

这套规则的取向很明确：**宁可丢，不可等**。对讲场景里迟到的语音没有价值，延迟累积才是致命的。

## 混音

`Mixer.mix` 是逐采样整数相加并饱和到 `[-32768, 32767]`，要求所有输入帧长度一致，否则抛异常。

### 网状房（WiFi / Nearby）

`RoomSession` 每个节拍把所有远端流解码后混合播放；没有任何解码结果时写入静音帧，保持 `AudioTrack` 的节拍不断。

### 蓝牙房——房主端混音

这是蓝牙房最关键的设计。`BluetoothMixPlanner.plan(memberIds, remotePcm, hostPcm, frameSamples)` 产出：

- `hostPlayback` —— 所有远端 PCM 的混音，供房主自己播放。
- `downlinks[recipientId]` —— 房主 PCM（若房主正按住 PTT）加上**除接收者本人以外**的所有远端 PCM。

每个下行有**独立的 `OpusCodec` 编码器**和**独立的 16 位序号计数器**。当没有内容可发时（房主没在说且没有其他远端在说），该下行会被跳过，不发静音帧浪费带宽。

为什么必须这样：RFCOMM 是星型点对点链路，客户端之间物理上无法直连，音频只能经房主转发。既然必须过一趟房主，那就顺便混好再发——否则房主要为每个客户端转发 N-1 路独立流，RFCOMM 的带宽根本撑不住。剔除接收者自己的声音则是避免听到自己的回声。

### 说话时静音本地播放

本地用户按住 PTT 期间，房主端与客户端都播放静音而非混音，避免自己的声音经链路绕回来形成回声。

另外，某个远端从「松开」切到「按下」时，它的 `RemoteStream`（抖动缓冲 + 解码器）会被**重建**，确保上一段话残留在缓冲里的音频不会在新一段话开头被放出来。

## 背压

`BluetoothSendQueue` 的音频容量是 3 帧。当第 4 帧音频入队时，**最旧的音频帧被丢弃**；信令帧永远不丢，且剩余顺序保持不变。`close()` 会唤醒阻塞中的 `take()`（返回 `null`），且已入队的帧先排空。

这是有意的：RFCOMM 链路拥塞时，丢掉 60 ms 前的旧音频远好过让队列无限增长、延迟越滚越大。

## 语音活动检测

`SpeakingDetector` 用 RMS 能量判断，阈值 500.0，挂起 15 帧（约 300 ms）——即能量低于阈值后仍保持「说话中」状态 300 ms，避免词与词之间的停顿导致指示灯闪烁。

仅**网状房**用它驱动「正在说话」指示；**蓝牙房直接用 PTT 状态**驱动，因为 PTT 本身就是明确的说话意图。

## 自测回环

`LoopbackController` 在单台设备上跑完整链路：麦克风 → 编码 → 抖动缓冲 → 解码 → 扬声器。用于在没有第二台设备时验证音频栈是否正常。入口在首页，对应 `Screen.LOOPBACK`。

排查「没声音」问题时，这是第一个该跑的检查——它能立刻区分是音频栈坏了还是网络链路坏了。
