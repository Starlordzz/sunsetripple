# 音频管线

采样、编码、抖动缓冲、混音、播放全部在**原生侧**完成（Android Kotlin、iOS Swift、HarmonyOS ArkTS），Dart 只负责搬运 Opus 包。这条分工是有意的：抖动缓冲和混音必须跟着音频时钟走，Dart 的 `Timer` 有调度漂移；每帧搬运 PCM（640 字节）也比搬 Opus 包（约 60 字节）贵一个数量级。

## 参数总表

| 参数 | 值 | 定义位置 |
| --- | --- | --- |
| 采样率 | 16 000 Hz | `OpusCodec.SAMPLE_RATE`（Android）；Swift 侧同值 |
| 帧长 | 20 ms | 原生采集/播放循环 |
| 帧采样数 | 320（16 位单声道 PCM，640 字节） | `OpusCodec.FRAME_SAMPLES` |
| 编解码 | Opus，`OPUS_APPLICATION_VOIP`，单声道 | `OpusCodec.kt`（**仅 Android**） |
| Opus 实现 | Concentus 1.0.2（纯 JVM） | `android/app/build.gradle.kts` |
| Opus 输出上限 | 512 字节 | `OpusCodec.MAX_PACKET_BYTES`，与 `Frame.maxPayloadSize` 对齐 |
| 上行码率（WiFi / Wi-Fi Direct 全双工） | 24 000 bps | `RoomSession._wifiBitrate` |
| 上行码率（蓝牙 PTT） | 16 000 bps | `RoomSession._bluetoothBitrate` |
| 采集源（Android） | `VOICE_COMMUNICATION`，可用时挂载硬件 AEC / NS / AGC | `PlatformAudioPlugin.kt` |
| 播放属性（Android） | `USAGE_VOICE_COMMUNICATION` + `CONTENT_TYPE_SPEECH`，`CHANNEL_OUT_MONO`，`MODE_STREAM` | `PlatformAudioPlugin.kt` |
| 缓冲区大小（Android） | `max(minBufferSize, 640 * 4)`，采集与播放同规则 | `PlatformAudioPlugin.kt` |
| 采集/播放（iOS） | AudioUnit VoiceProcessingIO（`.playAndRecord` / `.voiceChat`） | `PlatformAudioPlugin.swift` |
| 混音满量程分母 | 32768 | C / Kotlin / Swift / Dart 四端一致 |

选 16 kHz 宽带单声道是语音场景的常规折中：比 8 kHz 窄带清晰得多，又远比 48 kHz 省带宽与 CPU。20 ms 帧长是 Opus 的默认甜点，兼顾编码效率与延迟。

## 链路

```mermaid
flowchart LR
    MIC["麦克风"] --> CAP["原生采集线程<br/>AudioRecord / VoiceProcessingIO"]
    CAP --> ENC["Opus 编码<br/>（仅 Android）"]
    ENC --> EV["EventChannel<br/>Opus 包 + level"]
    EV --> DART["Dart: RoomSession<br/>按房型决定是否发送"]
    DART --> TX["传输层"]
    TX -.->|"网络"| RX["传输层"]
    RX --> SUB["Dart: submitRemoteFrame"]
    SUB --> PB["原生播放线程"]
    PB --> JB["抖动缓冲<br/>每个远端一个"]
    JB --> DEC["Opus 解码 / PLC"]
    DEC --> MIX["饱和混音"]
    MIX --> SPK["扬声器<br/>AudioTrack / VoiceProcessingIO"]
```

播放节拍由原生播放线程定速：Android 靠**阻塞式 `AudioTrack.write`**（写满即阻塞，天然形成 20 ms 时钟），iOS 靠 AudioUnit 的渲染回调。都不需要额外的定时器。

## Dart 抽象

`lib/core/audio/audio_io.dart` 定义 `AudioIo` 接口，`lib/core/platform/platform_audio_channel.dart` 的 `PlatformAudioChannel` 是它的平台实现：

- MethodChannel `host.msknet.sunsetripple/audio`：`startCapture`、`stopCapture`、`submitRemoteFrame`、`removeRemoteMember`、`clearRemoteMembers`、`setMuted`、`setSpeakerphone`、`setUseBuiltinMic`、`setBitrate`、`stopPlayback`、`dispose`。
- EventChannel `host.msknet.sunsetripple/audio_events`：原生上行事件为 `{data: Uint8List, level: double}`。Android 上 `data` 是 Opus 包，`level` 是这一帧的归一化响度（0~1）。

测试与桌面占位使用 `MockAudioIo`。

## 采集与发送

`RoomSession._startAudioPipeline` 调用 `audioIo.startCapture`，并在回调里决定是否发送：

- **全双工（WiFi / Wi-Fi Direct）**：只要没静音就发送。
- **PTT（蓝牙）**：没静音且 `isPttPressed` 为真才发送。

码率按房型选择（全双工 24 000、蓝牙 16 000）。回调里的 `level` 以 33 ms 节流（约 30 Hz）送进 `waveStream`，驱动界面水波。

需要说明的是，上行数据是**已编码的 Opus 包**，不是 PCM；原生侧在事件里附带 `level` 供界面显示。

## 原生实现

### Android

`android/app/src/main/kotlin/host/msknet/sunsetripple/PlatformAudioPlugin.kt`：

- 采集线程读满 320 采样后计算 RMS（除以 32768 归一化），用 Concentus 编码为 Opus 包，经 EventChannel 上抛。
- 播放线程每 20 ms 取一帧：对每个远端流从抖动缓冲拉包、Opus 解码（丢包走 PLC），逐采样相加并饱和到 `[-32768, 32767]`，写进 `AudioTrack`。没人说话时写静音帧，保持时钟连续。
- `submitRemoteFrame` 解析 6 字节帧头（`[1]` 发送方、`[2..3]` 序号、`[4..5]` 载荷长度），把载荷分流进各发送方专属的抖动缓冲。
- 采集源为 `VOICE_COMMUNICATION`，可用时挂载 `AcousticEchoCanceler` / `NoiseSuppressor` / `AutomaticGainControl`；采集与播放会走同一套通信音频路由。

Concentus 不在 iOS 使用——它只是 Android 侧的实现选择。

### iOS

`ios/Runner/PlatformAudioPlugin.swift` 使用 AudioUnit 的 VoiceProcessingIO，采集与播放都走 16 kHz / 单声道 / 16 位 RAW PCM：

- 采集回调计算 RMS（同样除以 32768）并上抛 `{data: PCM 字节, level}`。
- 收到远端帧后按发送方分流进内存队列（上限 10 帧），渲染回调逐采样相加并做饱和截断后输出。

**已知缺口：iOS 侧没有 Opus。** 收到的远端载荷被直接当作 RAW PCM 处理，而 Android 上行的是 Opus 包。因此当前 iOS 与 Android/Opus 链路之间**无法互通语音**，iOS 只是端到端的 PCM 路径。这一点在文档里必须如实标注。

### HarmonyOS

`harmonyos/entry/src/main/ets/audio/HarmonyAudioEngine.ets` 是 ArkTS 主机的音频引擎，使用 `AudioCapturer` / `AudioRenderer` 与 `SOURCE_TYPE_VOICE_COMMUNICATION` / `STREAM_USAGE_VOICE_COMMUNICATION`，同样是 16 kHz 单声道 RAW PCM（无 Opus）。`HarmonyRoomSession.ets` 负责把它与 PTT 状态接起来。

## 抖动缓冲

Android 原生侧每个远端流一个 `JitterBuffer`（`android/.../audio/JitterBuffer.kt`），按 16 位回绕序号缓存 Opus 包：

- **预缓存**——必须先攒够 3 帧才开始输出。
- **乱序重排**——序号靠后的包先到会被暂存，按序输出。
- **丢包**——`poll()` 返回 `PollResult.Lost`，调用方把 `null` 喂给解码器触发 **Opus PLC**（丢包补偿）。
- **未就绪**——`PollResult.NotReady`：预缓冲未满或欠载，这一拍不出声，不推进指针，也不要用 PLC 硬补。
- **迟到丢弃**——起播后序号小于当前位置的帧直接丢掉。
- **溢出**——超过 10 帧时丢最旧的。
- **重对齐**——空洞大于缓冲上限时，`next` 对齐到当前最小序号，避免永远追不上。

取向很明确：**宁可丢，不可等**。对讲场景里迟到的语音没有价值，延迟累积才是致命的。

iOS 侧没有这套重排/PLC 逻辑，只有按发送方的大致队列（上限 10 帧），简单丢最旧。

## 混音

原生播放循环自己做逐采样整数相加并饱和到 `[-32768, 32767]`（Android 的 `playbackLoop`、iOS 的 `providePlaybackPcm` 各自实现）。此外 `native/src/audio_dsp.cpp` 提供 C++ 版：

- `sunset_mix_pcm_streams`——多路 16 位 PCM 线性混音，带饱和截断；单路时直接 `memcpy`。
- `sunset_calculate_rms`——归一化 RMS，满量程分母固定 32768。

两者经 `lib/core/ffi/native_core_ffi.dart` 的 `NativeCoreFfi` / `NativeRingBuffer` 暴露给 Dart，原生库不可用时回退到等价的纯 Dart 实现。Android 通过 `externalNativeBuild`（`native/CMakeLists.txt`）打包 `libsunset_ripple_native.so`。

## 说话指示

原生侧只上报 `level`；「谁在说话」由 Dart 的 `RoomSession` 推断：

- 收到某个**在册成员**的音频帧时调用 `audioIo.submitRemoteFrame`，并把该成员标记为正在说话；不在册的 `senderId` 会被丢弃，防止伪造来源在原生侧凭空建出解码器。
- **全双工**没有 PTT 松手事件，靠音频停流判定：400 ms 没再收到音频就熄灭指示（100 ms 一次的看门计时器）。
- **PTT 房**直接由 `pttState` 帧驱动，因为 PTT 本身就是明确的说话意图。

界面水波由 `waveStream` 的 `level` 驱动，与说话指示是两条独立的数据流。

## 诊断面板

`lib/ui/pages/diagnostics_sheet.dart` 显示会话真实统计，而非写死的默认值：

- 音频格式：`Opus · 16 kHz · 单声道 · 20 ms`（`AppStrings.audioCodecDescription`）。
- 丢包率：`RoomSession.packetLossPercent`，按各发送方的序号缺口估算。
- 往返延迟：`RoomSession.roundTripTimeMs`，客户端从发出 JOIN 到收到首份名单的实测耗时；房主侧为 `null`，显示为 `—`。
