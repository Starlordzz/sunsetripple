## 常用命令

```powershell
# 1. 获取依赖包
flutter pub get

# 2. 运行自动化单元测试 (144 个用例)
flutter test

# 3. 运行代码静态分析
flutter analyze

# 4. 在真机上调试运行
flutter run

# 5. 打包 Release 发布版 APK
flutter build apk --release
```

## 发布签名

### 密钥与配置

签名配置和密钥**只存在于本地**，不进入版本库。`.gitignore` 已排除 `keystore.properties`、`*.jks`、`*.keystore`、`*.p12`。

`keystore.properties` 格式见 `keystore.properties.example`：

```properties
storeFile=C:/Users/<用户名>/.android/sunset-ripple-release.p12
storePassword=<强密码>
keyAlias=sunset-ripple
keyPassword=<强密码>
```

> **同一密钥必须长期沿用。** Android 以签名证书标识应用来源，换密钥后已安装的用户无法覆盖升级，只能卸载重装。请离线备份 `.p12` 与密码。

### 签名守卫（alpha.14 修复）

`android/app/build.gradle.kts` 在 `assembleRelease` 的 `doFirst` 里做守卫：找不到
`android/key.properties` 时**直接失败**并打印三条修复路径，绝不静默回落到 debug 签名。

> **为什么这是硬约束**：此前 CI 拿不到签名材料，`flutter build apk --release` 必然
> 走 debug 签名分支，而 GitHub runner 每次现场生成新的 debug 密钥——**每个 release
> 的签名都不同**，用户升级会撞上 `INSTALL_FAILED_UPDATE_INCOMPATIBLE`，只能卸载重装。
> 从 alpha.14 起，`release.yml` 会从 secrets 还原 keystore，并额外用 `apksigner`
> 断言产物不是 `CN=Android Debug`。

本地自测若要接受不可发布的包，显式加 `-PallowDebugSigning=true`。

### 打包

```powershell
$env:JAVA_HOME='C:\Path\To\jdk-17' # 替换为本机 JDK 17 安装目录
.\gradlew.bat :app:testDebugUnitTest :app:lintRelease :app:assembleRelease :app:bundleRelease
```

产物：

- 可侧载 APK：`app/build/outputs/apk/release/app-release.apk`
- 应用商店 AAB：`app/build/outputs/bundle/release/app-release.aab`

配置签名材料：

```bash
bash scripts/setup-release-signing.sh
```

该向导会生成 PKCS12 长寿命密钥、写入 Gradle 实际读取的 `android/key.properties`，
并在 `gh` 可用时把 `ANDROID_KEYSTORE_BASE64` / `ANDROID_KEYSTORE_PASSWORD` /
`ANDROID_KEY_ALIAS` / `ANDROID_KEY_PASSWORD` 四个 repository secret 配好。

> **注意**：alpha.13 及之前该向导写的是仓库根 `keystore.properties`，
> 而 Gradle 读的是 `android/key.properties`（`rootProject` = `android/`），
> 因此跑完向导本地 release 仍回落 debug 签名。已在 alpha.14 修正。

### 发布到 GitHub Release

已发布版本见 [Releases](https://github.com/Starlordzz/sunsetripple/releases)。`.github/workflows/release.yml` 会在推送 `v*` Tag 后自动完成测试、还原签名材料、构建 Release APK、校验签名与打包 GitHub Release 上传，同时产出未签名 iOS `.ipa` 与 HarmonyOS 源码工程 zip。

首次启用前，在 GitHub Actions Secrets 配置 `ANDROID_KEYSTORE_BASE64`、`ANDROID_KEYSTORE_PASSWORD`、`ANDROID_KEY_ALIAS`、`ANDROID_KEY_PASSWORD` 四个值（`scripts/setup-release-signing.sh` 可自动写入）。keystore 必须离线备份。

> **尚未实现**：文档过去提到的 `update.json` 清单签名、APK SHA-256 校验与
> 应用内自动安装链路在当前代码中**并不存在**——`UpdateService` 只做 SemVer 比较，
> 并把 `html_url` 存下来供展示，没有任何下载/安装/校验动作。相关脚本
> （`scripts/SignUpdateManifest.java`、`GenerateUpdateSigningKey.java`）只产出密钥与清单，
> 没有消费方。接入之前不要对外宣称「更新包已做完整性校验」。

发布步骤：

1. 更新 `versionCode` / `versionName`（`pubspec.yaml` 与 `harmonyos/AppScope/app.json5` 两处）与 `CHANGELOG.md`。
2. 提交变更并创建同名 Tag，例如 `v0.1.0-alpha.11`。
3. 推送 Tag：`git push origin v0.1.0-alpha.11`。
4. Actions 自动创建版本 Release，并更新 `updates-prerelease` 或 `updates-stable` 滚动清单。

alpha / beta Tag 自动标记为 prerelease；手动运行 workflow 时，输入的 Tag 必须已存在且与 `versionName` 完全一致。

## 发布构建说明

当前发布构建为 `0.1.0-alpha.13`。更新协议会验证清单签名、APK SHA-256、包名和 Android 签名证书后，再交给系统安装确认。语音链路不依赖互联网，只有用户手动检查更新时才会访问 GitHub。
