# Alpha 4 之后的软件升级计划

> **状态：执行中。** 本计划基于 `0.1.0-alpha.4`，优先改善 Android 单平台的产品完整性、可靠性和可维护性；iOS 与 HarmonyOS NEXT 仍按《多平台设想》单独评估，不作为本计划前置条件。

截至 2026-08-17，阶段 1 的“关于与更新”首个垂直切片已落地：主页入口、运行时版本、GitHub 跳转、可展开的 CHANGELOG/许可证/隐私说明，以及纯 JVM 更新状态模型均已接入。签名更新清单、下载与安装仍未开始；阶段 0、2、3、5 尚未开始，阶段 4、6 只有既有基础能力，均未达到本路线图验收标准。

## 一、目标与原则

- 让用户能在不离开应用的情况下理解项目、获取更新并安全升级。
- 保持语音链路“近场、点对点、默认不依赖互联网”；版本检查必须明确、可控、可关闭。
- 多语言首期只支持简体中文和英语，**完全跟随系统语言自动切换，不增加手动语言按钮**。
- 继续使用可在纯 JVM 测试的决策模块；Android API 只留在适配器（Adapter）层。
- 所有用户可见功能先经过 API 35 模拟器，再经过至少 3 台真机的验收。

## 二、阶段 0：整理应用编排模块

**问题：** `MainActivity` 已超过 1,100 行，页面导航、权限、房间生命周期、通知意图和转场状态集中在同一处，后续增加更新与语言功能会继续扩大修改面。

**计划：**

- 提取 `AppCoordinator` 或 `AppViewModel`，只向 Compose 暴露不可变 UI 状态和少量事件入口。
- 将房间启动/结束、权限前置检查、主题与语言状态分别放入独立模块。
- 为导航、进程重建、旋转配置变化补齐 `SavedState` 恢复策略。
- 让更新模块通过小接口暴露 `check()`、`download()`、`install()` 结果；GitHub 与 Play 的实现作为不同 Adapter。

**验收：** `MainActivity` 只负责宿主和依赖组装；房间、更新、主题、语言模块均可用纯 JVM fake 测试。

## 三、阶段 1：关于页面、GitHub 入口与自动更新

### 1.1 入口设计

首页头图右上角继续只放昼夜主题按钮。首页底部麦克风检查区域之后新增一条低权重页脚：

`v0.1.0-alpha.4 · GitHub 项目 · 检查更新`

点击后打开“关于与更新”底部页，包含当前版本、更新状态、GitHub 项目、CHANGELOG、许可证和隐私说明。GitHub 按钮使用系统浏览器打开 `https://github.com/Starlordzz/sunsetripple`，不放进建房主流程。

### 1.2 更新协议

- 每个 Release 附带签名的 `update.json`、APK 和 AAB。
- 清单包含 `versionCode`、版本名、更新通道、最低版本、APK URL、SHA-256、变更摘要和签名。
- App 内置公钥，先验证清单签名，再验证 APK 哈希、包名和签名证书指纹。
- 默认只提供手动检查；用户开启“自动检查”后每天最多检查一次，进入房间或通话期间禁止检查。
- 稳定版和测试版分开选择；alpha 用户可以接收 pre-release，普通用户只接收稳定版。
- 下载完成后必须交给系统安装确认，不允许静默安装。

### 1.3 分发差异

- GitHub 版：允许应用内下载 APK，并按 Android 规则申请安装未知来源包权限。
- Play 版：使用 Google Play In-App Updates，不声明 GitHub APK 安装权限。
- 更新检查开启后，README 中“无互联网”统一改成“语音链路不依赖互联网”；明确说明版本检查会访问 GitHub。

**验收：** 断网、旧版本、同版本、测试版、哈希错误、签名错误和取消安装均有明确 UI 结果；更新失败不能影响当前通话。

## 四、阶段 2：系统自动多语言

### 2.1 范围

首期支持：

- 简体中文：`zh`，作为默认回退语言。
- 英语：`en`，系统语言为英语或英语区域时自动使用。

不提供语言设置入口、不增加手动切换按钮、不在应用内保存语言偏好。系统语言变化后，应用重启或重新创建 Activity 时生效；通话不会因语言变化中断。

### 2.2 实现

- 把所有界面文案、错误提示、权限说明、通知文字和无障碍描述移入 `res/values/strings.xml` 与 `res/values-en/strings.xml`。
- 使用资源参数处理昵称、人数、版本和状态，不拼接半句中文或英文。
- 保留协议错误码和日志中的稳定英文标识，用户可见文本统一走资源。
- 为自绘按钮补齐 `contentDescription` 的中英文资源；图标和动画不因语言改变几何尺寸。
- 未支持的系统语言自动回退到简体中文；英文翻译缺失时按 key 级别回退，不显示空白。

### 2.3 验收

- API 35 模拟器分别使用 `zh-CN`、`en-US` 和未支持语言启动，首页、扫描页、房内页、通知、权限错误和更新页无硬编码中文残留。
- 1.3 倍和 1.5 倍字体下，英语长文本不截断、不覆盖按钮和底部操作。
- 新增资源完整性测试：中文 key 与英文 key 集合一致，格式占位符一致。

## 五、阶段 3：安全与隐私

- 在现有握手之上增加身份认证和会话密钥协商。
- 使用 AEAD（优先 ChaCha20-Poly1305 或 AES-GCM）保护语音帧和控制帧；密钥只存在内存中。
- 提供短码或二维码显示设备指纹，首次入房明确展示“正在连接的设备”。
- 蓝牙房主转移不再依赖非安全重连，至少要有用户可见的风险提示和重新确认路径。
- 诊断导出默认不包含音频、昵称原文、设备地址和密钥材料。

## 六、阶段 4：可靠性与真机矩阵

优先闭合当前已知限制：

- 3～6 台设备的连续 A→B→C 房主转移。
- WiFi 系统确认弹窗、定位/附近设备权限和 P2P 组消失。
- 锁屏、后台、进程被系统回收、通知栏离开和重新打开应用。
- 蓝牙配对、断线重连、房主转移和语音恢复耗时。
- 设备能力差异：无 Nearby、无 WiFi Aware、低内存和低端蓝牙芯片。

每项记录设备型号、Android 版本、房型、步骤、日志摘要和是否恢复成功；未通过的组合不能标记为稳定版。

## 七、阶段 5：性能与音频质量

- 加入 Macrobenchmark、Baseline Profile 和建房转场帧时间门禁。
- 关注低端机首帧、主题切换、扫描列表滚动、房间成员变化和通知返回。
- 根据丢包、抖动和 RTT 自适应 Opus 码率、PLC 和抖动缓冲深度。
- 在房内显示低频、非打扰式的网络质量状态，不用持续动画制造噪声。
- 记录音频 underrun、平均恢复时间和端到端延迟；诊断数据只在用户主动导出时生成。

## 八、阶段 6：连接体验、无障碍与诊断

- 增加房间短码或二维码确认，降低同名设备误选概率。
- 首页、扫描页和房内工具栏支持 TalkBack、键盘/辅助操作、大字体和足够触控区域。
- 提供“导出连接诊断”入口，生成不含音频的权限、设备能力、连接阶段、丢包和错误日志。
- GitHub Issue 模板预填版本、房型和诊断摘要，但发送前必须由用户确认。

## 九、建议执行顺序

1. 阶段 0：整理应用编排模块。
2. 阶段 1：关于页面、GitHub 入口和签名更新清单。
3. 阶段 2：系统自动中英文资源化。
4. 阶段 4：三机以上真机可靠性矩阵。
5. 阶段 5：性能与音频质量基线。
6. 阶段 3：认证加密与设备指纹。
7. 阶段 6：连接体验、无障碍和诊断导出。

## 十、Alpha 5 发布门禁

- 中英文资源 key 集合一致，系统自动切换无手动语言按钮。
- GitHub 项目入口可用；更新清单签名、哈希和取消安装路径均有测试。
- `MainActivity` 不再承载更新下载和语言资源选择逻辑。
- 3 台以上真机完成 WiFi、蓝牙、锁屏和一次房主转移验收。
- `testDebugUnitTest`、`assembleDebug`、`lintDebug` 和性能基线全部通过。
- README、CHANGELOG、仓库 Wiki 和 Release notes 的版本、功能和已知限制保持一致。
